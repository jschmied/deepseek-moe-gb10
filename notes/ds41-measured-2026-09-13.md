# DeepSeek-V4.1-Flash, measured on the box — routing, residency, read path

2026-09-13. Everything below is DS4.1's own routing, not Qwen's. Until today every residency number
we had was measured on Qwen3.8-Flash-Next and carried the caveat "the directions transfer, the levels
do not". Several of the levels turned out not to transfer, and one direction reverses.

## How the trace was taken

`tools/expert_trace.py` in the fork streams the model **one layer shard at a time**: every sequence
is pushed through layer L (one 7.4 GB shard) before layer L+1 is touched, so at most one layer's
weights are live and the 510 GB checkpoint never has to be resident. The 40 layer shards came off the
backup server over LAN at 103 MB/s, two ahead of the tracer, deleted behind it; peak local footprint
was three shards. Engram rows for layers 1 and 14 were pulled by HTTP range request — 5,034 requests,
66 MB, 61 s — instead of the two 101 GB tables. Corpus: `trace_corpus_v3.jsonl`, 95 sequences,
17,704 tokens, coding + general. Wall time 51 minutes for 40 layers.

The router is **unmasked** — this is what the model actually wants to route to, not what
`PRUNE_KEEP` leaves routable. The port validated end to end on the same pass: teacher-forced top-1
accuracy **81.6 % on coding (NLL 0.996)** and 46.9 % on general (NLL 3.350).

Trace: `notes/data/ds41-routing-unmasked.npz` (57 requests after dropping sequences under 64 tokens,
40 layers, top-6, 384 experts). Run log and full output in `notes/data/ds41-*-20260913.txt`.

## 1. The arena is 34 %, not 44 %, and the traffic is 0.58 GB/token

`EXPERT_BYTES = 3 × (2304×2560 + 2304×160) = 18,800,640` (`engine/experts.py:46`), which the shard
headers confirm: six tensors per expert, 17.93 MiB, laid out as **two runs** — a 1.05 MiB scale run
and a 16.88 MiB weight run about 585 MB apart, each starting unaligned (offset mod 4096 = 3896 and
1592), so O_DIRECT overreads exactly one page per run: **8 KiB on 18.8 MB, 0.04 %**. That is
negligible, as ds-08 said.

So a 98 GB arena is **5,212 slots = 33.9 %** of the 15,360 (layer, expert) pairs, and 90.5 GB is
4,813 = 31.3 %. The 44 % we have been quoting is a CB3 3-bit number, from the packing the
`<!DOCTYPE>` degeneration pulled back from.

Simulating `ExpertStore` faithfully — one global LRU keyed `(layer, expert)` across all 40 layers,
plus the FIFO ring that absorbs prefill misses — over a held-out stream of 12 requests:

| arena | slots | best coverage | misses/token | **GB/token** |
|---|---|---|---|---|
| 98 GB | 5,212 (33.9 %) | 83.9 % | 31.0 | **0.582** |
| 90.5 GB | 4,813 (31.3 %) | 81.9 % | 34.0 | 0.639 |
| 60 GB | 3,191 (20.8 %) | 73.5 % | 50.6 | 0.951 |

**This is the number that reframes the project.** The survey assumed 271 MB/token at ~93 % coverage.
The real figure at the shipped arena is **0.582 GB/token at 83.9 % coverage** — more than twice the
traffic, because both inputs were wrong: the arena is 34 % not 44 %, and coverage is 84 % not 93 %.

At the read rate the engine's own reader actually achieves (section 3, 5.2 GB/s at one expert in
flight) that is **112 ms/token of NVMe alone, an 8.9 tok/s ceiling** for the full-quality unpruned
path even with a perfect schedule. At the 2.68 GB/s it measures today it is 217 ms/token → 4.6 tok/s,
which is where the observed 2.68 tok/s comes from once compute is added.

The consequence for the roadmap: fixing the schedule is worth about 2×, and then the path is **still
bandwidth-bound**. Everything beyond that has to remove bytes, not reorder them.

## 2. Their residency design is right, and their code default is not

Coverage at the 98 GB arena, varying only `transient_slots` (the FIFO ring that keeps a long prompt
from evicting the decode working set):

| transient | cold start | with the global warm start |
|---|---|---|
| 0 (prefill into the LRU) | 82.04 % | 82.51 % |
| **8** (`env.example`) | 82.80 % | **83.88 %** |
| 100 | 82.66 % | 83.69 % |
| 400 (the code default) | 81.90 % | 82.71 % |
| 1000 | 80.46 % | 81.09 % |

* The ring earns its slots: 8 beats 0 by **+1.4 pp**. Their reasoning holds on their own model.
* But `ExpertStore.__init__` defaults `transient_slots=400`, which is **−1.2 pp** against the 8 that
  `env.example` sets. Anyone constructing the store in Python without the env file gets the worse
  number. Change the default to 8.
* The global warm start is worth **+1.0…+1.1 pp** at every ring size — small, free, keep it.
* **One global pool beats per-layer budgets** (82.71 % vs 82.22 %), confirming ds-05 on DS4.1.

Prefill-warming — seeding the arena from the request's own prompt — is **negative here**: −5.1 pp at
34 %/10 % dynamic, −3.1 at 20 %/10 %, +1.2 at best. The prompts in this corpus are 17–31 tokens, well
under the 256–1,024 that ds-10 found necessary, so this is consistent with Qwen rather than new
evidence. Closed on both models.

## 3. The read path is not the problem — and neither of the two config levers is real

`tools/expert_read_bench.py` imports the engine's own `ExpertStore` and times `_read_leased`, so this
is the shipped code, not a re-implementation. Median of 3, 48 expert reads per cell, on real shards:

| `DSV41_IO_THREADS` | conc 1 | conc 2 | conc 4 | conc 8 |
|---|---|---|---|---|
| 1 | 4.94 | 5.23 | 5.29 | 5.21 GB/s |
| 2 | 5.04 | 5.60 | 5.89 | 5.77 |
| 4 | 5.08 | 5.67 | 5.87 | 6.21 |
| 12 (default) | 5.04 | 5.67 | 6.11 | 6.14 |

and varying `DSV41_READ_CHUNK_MB` at 12 io-threads: 2 MB → 4.68/5.82/6.13, 4 MB (default) →
5.18/5.49/6.18, 8 MB → 5.05/5.93/6.26, unsplit → 5.20/5.96/6.42 at conc 1/2/4.

* **`DSV41_IO_THREADS` is not a lever.** It saturates by 4 and the default is 12; a decode layer
  misses 0.5–1.6 experts, so the staging semaphore never binds. Survey idea 2a is dead.
* **`DSV41_READ_CHUNK_MB` is not a lever either.** Reading the expert unsplit is worth perhaps 3–8 %
  at one expert in flight and nothing beyond that. My earlier +41 % was a serial-chunking harness,
  not this engine — withdrawn this morning, and this is the measurement that settles it.
* **The read path gives 5.0–6.4 GB/s. Decode measures 2.68.** The gap is outside `_read_leased`.
  `resolve()` ends in `list(self.pool.map(...))` and `fastdecode.py:576` runs
  `gA[L].replay(); self._resolve(L); gB[L].replay()`, so every layer is GPU compute, host sync, NVMe
  with the GPU idle, GPU compute — 40 times per step, nothing overlapping across layers.

> **CORRECTED, same day — "that is where the missing 2× is" was wrong.** Measured with the engine's
> own `ExpertStore` and a real arena, `resolve()` itself costs **0.030 ms/layer** (1.19 ms/step) and
> its D2H barrier adds 2.0 ms/step: about 3 ms of a 1,108 ms step. The function is not expensive, it
> is only a *barrier*. Replaying the real per-layer miss pattern through the shipped path costs
> **365.0 ms/step**; taking the H2D and `stream.synchronize()` out of the staging lease costs 310.3
> (**−15 %**), batching the submit across layers 314.3 (**−14 %**). Layer depth is thin because a
> layer misses **2.52 experts on average, median 2, and 14.8 % of layers miss none**. A third
> component nobody had named: the Engram small reads contend with the O_DIRECT expert bursts for
> **+21 %** (380 → 459 ms/step), a quarter of which `sys.setswitchinterval(5e-4)` recovers for free.
> Together **≈1.25–1.35×, i.e. 2.68 → 3.4–3.6 tok/s**, not 5–6. A *perfect* schedule at this arena
> would be ~103 ms/token → ~9.7 tok/s and nothing measured approaches it.

## 4. Widening the verify block is free in bytes — the conflict is resolved

Distinct experts a layer touches over k consecutive decode tokens, measured:

| block k | distinct/layer | per step (40 layers) | marginal | per verified token |
|---|---|---|---|---|
| 1 | 6.00 | 240.0 | | 240.0 |
| 2 | 10.13 | 405.3 | +4.13 | 202.6 |
| 4 | 16.87 | 674.9 | +3.17 | 168.7 |
| **6** | **22.56** | **902.5** | +2.74 | **150.4** |
| 8 | 27.53 | 1101.1 | +2.39 | 137.6 |

The stored 20.96 experts/layer at block 6 was 7 % low; the real figure is 22.56. More usefully, the
marginal cost of a position **falls** from +4.13 to +2.39 experts per layer, so per *verified* token
the arena traffic drops 240 → 137.6 from k=1 to k=8 — widening is sublinear and, in bytes, free.

> **RESOLVED, same day.** I wrote here that per *accepted* token the sign might flip (291 reads at
> block 6 against 324 at block 8) and that acceptance-vs-k was the missing input. That double-counts.
> Measured on the real trace through the faithful cache at the 98 GB arena, **misses per accepted
> token are invariant in the block width**: 24.0 / 24.0 / 24.0 / 24.0 at blocks 4/6/8/12 for
> acceptance 2, and 24.1 / 23.9 across the same sweep at acceptance 3 and 4. The extra positions'
> experts are exactly the ones the *next* step would have fetched, so widening moves bytes forward in
> time and never adds them. Width is therefore decided on compute and acceptance alone — which is
> what the engine's own all-resident sweep already said (41.0 / 39.7 / 39.7 ms per accepted token at
> 4/6/8). Wider is also a small scheduling bonus: per-layer burst depth rises ~22 % from acceptance
> 2.70 to 3.45.

## 5. Prediction: the prize was an accounting artifact — WITHDRAWN

This section originally read "Prediction is worth far more on DS4.1 than on Qwen" and claimed a 5–6×
reduction in NVMe bytes, on the strength of an oracle arm that reached 96.9 % coverage against the
best real arm's 83.4 %. **That comparison is not sound and the conclusion is withdrawn.**

The oracle arm (ds-11) is a *static core ranked on the held-out request's own decode histogram* with
5 % dynamic. It is never charged for filling that core: ~95 % of the arena, about 93 GB, is
pre-loaded for free and only out-of-core touches count as loads. The honest ceiling for a
demand-paged cache is **Belady**, and measured on this trace through the faithful cache:

| arena | LRU (shipped) | Belady (perfect future) | ratio |
|---|---|---|---|
| 98 GB / 5,212 slots | 0.447 GB/token | 0.253 GB/token | **1.76×** |
| 73.8 GB / 3,925 slots | 0.628 | 0.349 | 1.80× |

**1.76×, not 5–6× — and it needs the entire future.** Gain against LRU by lookahead: 1 token 1.01×,
3 → 1.02, 6 → 1.03, 10 → 1.04, 20 → 1.08, 50 → 1.19, 200 → 1.61, ∞ → 1.76. A drafter supplies 5–8
tokens, i.e. **3–4 %**.

Four further kills, each measured:

* **DSpark cannot name the target's experts.** `config.json` gives it `dspark_n_routed_experts 128`,
  `dspark_num_experts_per_tok 3`, `dspark_target_layer_ids [37,38,39]`, and `FixedStore` gives it its
  own resident 3×128 arena. It shares the hidden state, not the 384-expert router. The premise I put
  in the brief was wrong.
* **Previous-step prefetch is a no-op by construction.** A verify step touches ~905 of 3,925 slots,
  so the previous step's set is still resident; the blocking misses are precisely what was *not* there.
* **Cross-layer prediction is far under the bar.** A co-occurrence predictor trained on 47 requests
  recalls 30.5 % of layer L's top-6 from layer L−1 (29.9 / 28.8 / 26.6 at d=2/4/8) against a
  popularity baseline of 14.4 %. Real signal, useless magnitude; our own stop-line was ~60 %.
* **Costed, it is worse than useless**: at 4 layers of lookahead, N=24 removes 2.3 % of blocking
  misses for +39 % bytes, N=48 removes 4 % for +2.3× bytes, N=96 is +10× bytes and negative.

Online policy is also nearly exhausted: LRU 84.13 %, SLRU/2Q 84.34 % (+0.2 pp), LFU 81.59 % (−2.5 pp).

**Measured 2026-09-15, `tools/prefetch_oracle.py` on `route-decode.jsonl`** — the "no-op by
construction" line above is now a number, and it is the strongest form of the result. Warmed on a
25 % prefix and scored on the suffix, at the engine's 4,788 slots:

| predictor (lookahead it needs) | raw overlap with S(L,t) | names this share of LRU's misses | bytes vs LRU |
|---|---|---|---|
| same layer, previous token (1 token) | 49.3 % | **0.0 %** | 1.00 |
| same layer, union of last 2 / 4 / 8 | 59.8 / 69.6 / 79.0 % | **0.0 %** | 1.00 |
| previous layer, same token (1 layer) | 5.5 % (chance = 5.7 %) | 5.6 % | **4.91×**, hit −8.8 pp |
| static top-22…73 per layer (held-out prefix) | — | 4.0 – 25.0 % | 1.05 – 1.90×, hit +0.1…0.3 pp |

The overlap is high and *entirely worthless*: at 83.7 insertions/token a 4,788-slot LRU already
holds ~57 tokens of history, and its misses are pairs last used **26 / 45 / 143 tokens ago**
(p10/p50/p90), only 7.1 % of them compulsory. Everything a k ≤ 8 predictor can name is already
resident, so the prefetch issues **zero extra fetches and changes nothing** — not a small win, an
exactly-null one. The required lookahead is ~45 tokens; a drafter gives 5–8. Cross-layer index
carry-over is at chance and, costed, is a 4.9× byte disaster. Ranking is unchanged at 3,000 slots.
**The whole predictor family is closed. The gap to Belady is a capacity/ordering problem, not a
knowledge problem.**

The reason is structural, and it is the useful thing this section can still say. A 435-token request
touches **8,282 distinct (layer, expert) pairs — more than the 5,212-slot arena** — and the working
set is still growing at +8.5 pairs/token after 400 tokens (240 after one token, 1,275 after ten,
4,648 after a hundred, 7,887 after four hundred). **There is no core to discover; the tail keeps
arriving.** So the byte term is fixed, and everything past the schedule fix has to *remove* bytes.

## What to do next, in order

1. **Attribute the last 19 %.** The schedule accounting above explains 893 ms of the observed
   1,108 ms/step. One streaming run dumping the counters that already exist in `ZERO_STATS`, plus one
   arm with `GRAPH_SEGMENTS` forced on in streaming mode (it is gated on `self.lut is not None`, so
   the streaming path runs 80 graph replays instead of 3), settles it before anyone writes code.
2. **Take the H2D off the staging lease** (−15 % of the load phase) and **issue the next block's
   Engram rows in the draft window** (−21 % contention). Both bit-exact, together ≈1.25–1.35×.
   `sys.setswitchinterval(5e-4)` is one line for +4 % under contention.
3. **Widen the verify block to 8** — bytes per accepted token are invariant, so this is decided on
   acceptance and compute alone. `DSV41_BLOCK=7`, one 200-token run.
4. Change `transient_slots`'s code default from 400 to 8 (−1.2 pp for anyone not using `env.example`).
5. **The one prediction channel left is token identity.** The tracer already has the token ids; dump
   them beside `routed` and measure top-6 recall of layer L's set from the next token id alone. Under
   ~50 %, close the prefetch family in writing.
6. Do **not** spend time on `DSV41_IO_THREADS`, `DSV41_READ_CHUNK_MB`, per-layer arena budgets,
   prefill-warming, drafter-driven prefetch, cross-layer prefetch, or eviction policy. All measured dead.

## 6. The CB3 arena repack is dead — the kernel is already at the memory rate

The first experiment out of the 2026-09-13 surveys was the bandwidth agent's top item: `_cb3v3_up_kernel`
launches 72 programs per expert and each touches **eight independent base pointers** (`w1/w3 ×
{lo,hi,cb,s}`), and a synthetic gather kernel showed 8-runs-per-program costing 142–147 GB/s against
195–227 for one run, *at a 90 GB footprint and not at 8 GB*. Estimated worth: +13 %, bit-exact.

`tools/cb3_kernel_bench.py` measures the **shipped path** instead of a synthetic: real `CB3ArenaV2`,
`moe_forward_v3`, block 6 × top-6, 16 rotating routing draws so the touched set changes between
reps, median of 3 starts × 30 reps. Correctness against the repo's own
`fp4_moe.moe_forward_reference` is 4.45–4.68e-03, inside its 5e-3 test threshold.

**The footprint effect does not exist in the real kernel.**

| arena | 5.6 GB | 14.8 | 29.6 | 44.4 | 59.2 | 75.3 | 89.6 |
|---|---|---|---|---|---|---|---|
| GB/s | 171.5 | 168.3 | 168.3 | 171.0 | 169.7 | 168.0 | 171.2 |

Flat within ±1 % over a 16× range of footprint. It also reproduces the stored **168.7 GB/s
(2026-09-11)** exactly, so that number is current — one stored figure that survived re-measurement.

Sweeping the bytes instead of the footprint says why, and says something more useful. At a 75.3 GB
arena, varying how many distinct experts a call touches:

| distinct | 4.0 | 8.0 | 14.6 | 18.0 | 23.6 |
|---|---|---|---|---|---|
| read MB | 57.8 | 115.6 | 210.5 | 260.2 | 341.5 |
| ms | 0.526 | 0.814 | 1.277 | 1.524 | 1.944 |
| apparent GB/s | 109.8 | 142.0 | 164.8 | 170.8 | 175.7 |

That is a straight line: **marginal rate 200.8 GB/s, fixed cost 0.235 ms per call** (pairwise slopes
200.7 / 205.0 / 201.2 / 193.6, so the fit is not an artifact of the endpoints). The apparent 168 GB/s
is not a slow kernel — it is a 200 GB/s kernel plus a per-call constant that is **15 % of the call**
at the real 22.56 distinct experts.

200.8 GB/s is **91 % of the ~220 GB/s** the dense chain achieves at realistic footprint. There is no
8-pointer penalty of the claimed size, so **the repack is not worth +13 % and should not be built.**
The expert path's remaining lever is bytes — CB2, the 2-bit scales — not layout.

**Caveat, and the next question.** This harness runs eager; the engine captures these kernels in CUDA
graphs, so part of the 0.235 ms constant is launch and allocation overhead that the engine does not
pay. Whether *any* of it survives graph capture is worth one measurement, because 40 layers × 0.235 ms
would be 9.4 ms of a ~115 ms step if it did. That is the follow-up, and it is cheap.

### 6b. Follow-up: the constant is not overhead, it is memory-level parallelism

The caveat above was that the harness runs eager while the engine captures these kernels in CUDA
graphs. Measured: **graph replay is 3.2 % faster than eager** (1.492 vs 1.541 ms at 18 distinct), and
re-fitting under capture gives marginal **200.0 GB/s** with the constant only falling 0.235 → 0.193 ms.
So the constant survives graph capture and is not launch overhead.

Two candidate explanations, one refuted:

* **Empty blocks — refuted.** `moe_forward_v3` takes `build_routing_small` at P ≤ 64, which sizes the
  grid by *pair* count, so a call touching 8 distinct experts still launches blocks for all P. Holding
  distinct at 8 and raising P from 36 to 60 leaves the bytes identical and costs **+0.010 ms** — about
  0.4 µs per empty block. Not the mechanism.
* **Occupancy — this is it.** The kernel simply does not saturate until enough experts are in flight,
  because each active block launches only 72 programs and there are 48 SMs:

| distinct experts in the call | 4.0 | 8.0 | 14.6 | 18.0 | 23.6 | 28.6 | 31.6 | 37.8 |
|---|---|---|---|---|---|---|---|---|
| GB/s (graph replay) | 122.0 | 149.8 | 168.5 | 172.2 | 181.0 | 181.2 | 182.5 | 188.0 |

So the affine fit was a curve read as a line. There is no constant to remove. The kernel reaches
**188 GB/s at 37.8 experts** and is still climbing, against ~220 GB/s for the dense chain — and at the
real decode point (block 6, 22.56 distinct) it sits at ~180.

**What that makes actionable.** The lever on this kernel is *experts in flight per launch*, which is
the same axis as verify-block width — and section 4 already showed width is **free in bytes**. Block 8
touches 28.6 distinct instead of 18.0 and runs at 181 GB/s instead of 173. So widening the block helps
twice: it amortises the dense term over more accepted tokens, and it raises the MoE kernel's own
efficiency. The other way to buy the same thing is batching sequences, which the bandwidth survey
already priced at ~+49 % aggregate.

### 6c. CB2 reproduces its stored ratio

Same harness, `CB2ArenaV2` + `moe_forward_cb2`, graph replay, 9,992,192 B/slot:

| distinct | 8.0 | 14.6 | 18.0 | 23.6 |
|---|---|---|---|---|
| read MB | 79.9 | 145.5 | 179.9 | 236.1 |
| ms | 0.639 | 1.022 | 1.210 | 1.522 |
| GB/s | 125.2 | 142.3 | 148.7 | 155.1 |

At the real 18 distinct, **CB2 is 1.210 ms against CB3's 1.511 — a wall ratio of 0.801**, which
reproduces the repo's stored 0.810 (2026-09-11). A second stored number that survives re-measurement,
and it confirms the +12 % step-time estimate for a CB2 tier is sound on the kernel side. Note CB2's
*rate* is lower at every point (155 vs 181 GB/s at 23.6 distinct): it reads 0.69× the bytes but
dequantizes 2-bit codes through a 4-entry codebook, so it is closer to ALU-bound. The win is bytes,
and it is smaller than the byte ratio implies.

### 6d. Verify width on the MoE kernel: free on this axis too

Sweeping the block width at the distinct-expert counts the **real trace** gives for each width
(k=4 → 16.87, k=6 → 22.56, k=8 → 27.53 per layer), CUDA-graph replay, 7,114-slot arena:

| block | distinct | read MB | ms | GB/s | ms per *verified* token |
|---|---|---|---|---|---|
| 4 | 17 | 245.7 | 1.414 | 173.8 | 0.354 |
| 6 | 23 | 332.5 | 1.854 | 179.3 | 0.309 |
| 8 | 28 | 404.7 | 2.207 | 183.4 | 0.276 |
| 10 | 32 | 462.6 | 2.521 | 183.5 | **0.252** |

The kernel rate is flat at ~180 GB/s once ≥23 experts are in flight, and **cost per verified token
falls monotonically, −29 % from width 4 to 10.** Combined with §4 (misses per *accepted* token are
invariant in width) this says width is free or better on both the IO and the kernel axes. **The only
thing that can make widening not free is acceptance as a function of k**, which is still the one
missing measurement and needs the engine.

Two controls, because the first pass produced two cliffs that were not real:

* Holding distinct at 28 and varying P: 2.172 / 2.208 / 2.220 ms at P = 36 / 48 / 60. Pair count is
  ~free, confirming §6b's empty-block result at a different operating point.
* `_pick_bm` returns 16 for every P ≤ 64, so none of these widths crosses a tile boundary — the BM
  explanation for the apparent cliff was wrong.

**Methodology correction, and it invalidated two of my own cells.** The first run reported 140.6 GB/s
at block 4 and 3.566 ms at block 10; repeated, those are 173.8 and 2.521. "Median of 3 starts" was
three timing loops *inside one process*, which misses process-to-process spread (Triton autotune,
clock state). With five separate **processes** per cell the spread is under 2 %. Every kernel number
in §6, §6b and §6c should be read with that in mind — the levels there were single-process, and
while their conclusions do not change (the footprint sweep was flat across seven sizes, the CB2/CB3
ratio reproduces a stored figure), the individual cells carry more uncertainty than stated.

### 7. `MAX_SEQ` costs 7 % of decode — but not all of it is the indexer

First job of the night queue. Same 62-token prompt and 512 output tokens in every arm, so the live
context is ~31 positions throughout while the indexer's scan width is `max_seq / 2 + 1`. Median of 3
runs per arm, each arm a fresh server.

| `MAX_SEQ` | indexer columns | TPOT | decode | expert hit | NVMe/run |
|---|---|---|---|---|---|
| 4096 | 2,049 | 155.5 ms | **6.43 tok/s** | 0.9014 | 203.5 GB |
| 8192 | 4,097 | 161.2 | 6.20 | 0.9001 | 213.3 |
| 32768 (our default) | 16,385 | 167.3 | **5.98** | 0.8943 | 219.3 |

Monotonic, and **7.0 % of decode between the ends**.

> **Superseded by §17 (2026-09-14).** I read this as the same defect class vLLM fixed in #56686 and
> wrote that it "confirms the shape is live here". It does not: with `ARENA_GB` pinned the whole
> effect vanishes (6.074 vs 6.080 tok/s across the same 8× range of columns). The 7.0 % was arena
> shrinkage. The two caveats below were right and should have been read as the answer, not as
> qualifications.

The magnitude is **not** cleanly the indexer, for two reasons visible in the table:

* **The cost is not linear in columns.** +2,048 columns costs +5.7 ms; +12,288 columns costs +6.1 ms.
  A scan that were purely width-bound would have made the second step six times the first.
* **Coverage moves with it.** NVMe rises 203.5 → 219.3 GB and the expert hit rate falls
  0.9014 → 0.8943 across the same arms. A larger `max_seq` allocates larger `ckv`/`ik`/window caches,
  the arena is auto-sized from what is left, so it holds fewer experts. Roughly 1.5 GB of caches
  between 4096 and 32768, about 100 slots of 5,673.

So the honest reading is **7.0 % total, of which an unknown part is arena shrinkage rather than scan
width**. Separating them is one more sweep with `ARENA_GB` pinned so coverage cannot move; queued as
`sweep-max-seq-pinned`.

**Tooling fix this exposed**: `start.sh` truncates `logs/server.log`, so every arm's arena line but
the last was gone by the time I looked. `env_sweep.py` now captures it per arm — the swept variable
changing cache sizing is exactly when that number is the confound.

### 8. Kernel work is worth about a third of face value here, because the GPU is idle

Two consecutive plans have now been ranked on "CB3 is ~63 ms of a ~117 ms verify step, so it is 54 %
of the work". That is **0xBakeer's `NOTES.md`** (1589, 1997) on an **all-resident** configuration.
Priced against our own measurements instead:

| | |
|---|---|
| CB3 MoE kernel, measured (`cb3_kernel_bench`, graph replay, block 6, 23 distinct) | 1.854 ms × 40 layers = **74.2 ms/step** |
| our step, measured (TPOT 163 ms × accept 3.5) | **570 ms** |
| CB3 as a share of **wall** | **13.0 %** |
| CB3 as a share of **GPU-busy** time (GPU is 32 % busy) | **40.6 %** |

Both are true and they are not in conflict: their 54 % is of a step that is essentially all GPU;
ours is of a step that is **68 % idle waiting on NVMe**. So on this box **a 10 % CB3 kernel win is
7.4 ms of 570 = 1.3 % end to end**, and DeepGEMM #394's packet layout (9.5 % at 1 token, 4.4 % at 8)
would be around **1 %** at our T=6.

**The consequence for ranking is general, not specific to CB3.** Until the GPU-idle gap closes, every
kernel optimisation on this box is worth roughly a third of its face value, while anything that
removes *waiting* is worth full value. That inverts the order of the two P0s: the prefill transpose
and the async staging/Engram pipeline attack the 68 %, the packet layout attacks the 32 %.

No profiler is needed to do better than this estimate — the engine already exports
`attn_s`, `moe_s`, `route_s`, `load_wait_s`, `lease_s`, `h2d_s`, `kernel_s`, `nvme_read_s`,
`engram_s` and `engram_read_s` on `x_engine_stats` (`v41_engine.py:655-666`). Queued as
`step-breakdown`, which is one request rather than a profiling session.

Two code claims from the plan, checked: the Sinkhorn iterations **are** already collapsed into one
Triton kernel (`hc_sinkhorn.py:15`, `iters` as a `constexpr`), so there is no launch train to fuse
away; and the verifier's argmax is **per row** (`fastdecode.py:411`, `lg.argmax()` inside the loop),
not a batched `[6, 129280]` reduction, so the split-reduction steal does not apply as written — and
at ~0.02 ms of a 570 ms step it would not matter if it did.

### 9. Widening the verify block is NOT free — §4's resolution was wrong, and wrong in an instructive way

`sweep-block-width` on the engine. Two of four arms crashed (below); the two that ran settle it:

| `DSV41_BLOCK` | verify width | TPOT | decode | accept_len | NVMe/run |
|---|---|---|---|---|---|
| 5 (default) | 6 | 164.4 ms | **6.08 tok/s** | 3.47 | 221.0 GB |
| 7 | 8 | 207.0 ms | **4.83 tok/s** | 3.30 | 266.0 GB |

**Width 8 is 20 % worse than width 6.** NVMe per run rises 20 %, and acceptance *falls* 3.47 → 3.30.

**This contradicts what §4 published, and the error was mine.** §4 said "misses per accepted token
are invariant in the block width — 24.0 / 24.0 / 24.0 / 24.0 at blocks 4/6/8/12". That sweep held

further outside its horizon and lands fewer tokens. I swept a variable while holding constant a
quantity that depends on it, and then wrote "RESOLVED".

experts a layer touches goes 22.56 → 27.53 (**+22 %**, §4's own measurement) while accepted tokens
per step go 3.47 → 3.30 (**−5 %**). Bytes per accepted token should therefore rise ~28 %; measured
NVMe per run rose 20 %. So §4's *union* numbers were right and only the conclusion drawn from them
was wrong.

**The shipped default is correct and should stay.** And the offline conclusions that fed this —
"free on bytes" (§4) and "free on the kernel" (§6d) — are both true *at fixed acceptance* and both
irrelevant, because acceptance is not fixed.

### 10. The step breakdown did not survive contact — and the reason is worth more than the numbers

`step-breakdown` ran to its sentinel and produced a table I threw away. `kernel_s` came out at
**−2,588 ms/step** and `nvme_read_s` at **6,067 ms/step** inside a request that took tens of seconds.
Neither is an engine fault; both are mine.

**Cause 1: the counters are cumulative over the whole request, prefill included.** Dividing them by
the *decode* step count attributes thousands of prefill expert loads to decode. A 94-token generation
had already read 150 GB, nearly all of it prefill. Fixed by running the same prompt at 64 and 512
tokens and differencing: prefill is identical in both, so the delta is decode alone.

**Cause 2: half the counters are not wall clock.** `read_s`, `h2d_s` and `lease_s` are accumulated
*inside the io-thread pool* (`experts.py:233, 291, 309`), so they are thread-seconds summed over 12
workers. `route_s`, `load_s`, `resolve_s` (`:460-465`) and `moe_s`, `attn_s` (`model.py:512, 524`)
are main-thread and are wall. Mixing the two in one column is meaningless, and the tool now labels
each.

**One genuine engine finding fell out**: `kernel_s = moe_s − resolve_s` (`v41_engine.py:664`) is only
valid in the **pruned all-resident** configuration. There `lut is not None`, `resolve()` is skipped,
`resolve_s` stays 0 and `kernel_s == moe_s`. On the unpruned streaming path `resolve_s` is large and
the subtraction goes negative — so anyone reading `kernel_s` off a streaming run is reading garbage,
silently.

Re-queued with the fix. The invalid first run is kept at
`notes/data/step-breakdown-firstrun-invalid-20260913.txt` rather than deleted, because the shape of
the error is the point: **a job can run to its sentinel, be recorded `done`, and still be wrong.**
That is the limit of the queue, stated when it was built, now demonstrated.

### 10b. Why the breakdown needed an engine change, after two failures from outside

The second attempt differenced the same prompt at 64 and 512 tokens, expecting prefill to cancel. It
produced **negative** `attn_s` and `moe_s` deltas — the longer run reporting *less* attention time
than the shorter one.

`_reset()` (`v41_engine.py:574`) zeroes **model, table and store stats at the start of every
request**. So `x_engine_stats` is a per-request total of prefill **plus** decode, and differencing two
requests differences two *prefills*. On this engine prefill dominates every I/O counter by orders of
magnitude — thousands of expert loads against tens — so the delta is prefill run-to-run noise with
the decode signal buried in it. Both of my attempts were structurally incapable of working, and the
second one only looked plausible because the first had failed for a different reason.

Fixed where it had to be fixed: `_snap_prefill()` freezes every counter at the prefill→decode
boundary and `decode_only` now rides on `x_engine_stats` beside the totals. Six lines of snapshot,
and it makes every future breakdown correct rather than needing this reasoning again.

The general lesson, and it is the third instance today: **a number that is exported is not thereby a
number that means what you want.** `kernel_s` is a valid subtraction only in the pruned
configuration; `read_s` is thread-seconds not wall; and every one of them is prefill-dominated unless
you snapshot.

### 12. The coverage curve, measured — and the simulator is pessimistic, not optimistic

`sweep-arena`, four arms, three runs each, arena pinned so the slot count is the only thing moving:

| `ARENA_GB` | slots | coverage | hit rate | MB/token | decode |
|---|---|---|---|---|---|
| 56.75 | 3,926 | 25.6 % | 0.7962 | 781 | **3.71 tok/s** |
| 68 | 4,704 | 30.6 % | 0.8689 | 507 | **4.89** |
| 79 | 5,465 | 35.6 % | 0.8903 | 433 | **6.00** |
| auto (82.1 GB) | 5,679 | 36.9 % | 0.8937 | 416 | **6.26** |

**Steep and then flat.** The first 11 GB of arena (56.75 → 68) buys **+7.3 pp of hit rate and +32 %
of decode**; the last 3 GB buys +0.3 pp and +4 %. We are sitting just past the knee, which is the
right place to be and is not an accident — `ARENA_GB` auto takes everything above the free-memory

**Against `ds41_engine_sim`, at matching slot counts:**

| slots | sim hit | engine hit | sim MB/tok | engine MB/tok |
|---|---|---|---|---|
| ~3,925 | 0.7721 | **0.7962** | 800 | **781** |
| ~4,750 | 0.8185 | **0.8689** | 639 | **507** |
| ~5,300 | 0.8388 | **0.8903** | 582 | **433** |

The simulator is **within 2.4 % at tight coverage and up to 34 % pessimistic at wide coverage** — it
under-predicts hit rate by as much as 5 pp and over-predicts bytes accordingly. Its *level* is sound;
its *slope* is too shallow.

**The likely cause is a workload difference, and it cuts both ways.** The simulator scores
**held-out** requests — every prompt novel. `bench.py` runs the *same* prompt three times (warmup
plus two measured, `isl=62` in every line), so by the measured runs the engine's LRU is warm for that
exact prompt. So the sim describes novel traffic and the bench describes repeated traffic, and a real
agent workload sits between them.

Two consequences worth carrying:

* **Our simulated projections are conservative.** The CB3 cache's 1.42× coverage benefit and the
  0.582 GB/token figure both came from the sim, so the real numbers are likely better — the measured
  416 MB/token at 36.9 % is already well under the sim's 582 at 33.9 %.
* **The 6.26 tok/s headline is a warm-LRU-on-a-repeated-prompt number.** It is the right figure for
  "the same request twice", which is what a benchmark is, and an optimistic one for first-contact
  traffic. Worth saying whenever it is quoted.

### 13. `DSV41_IO_THREADS` is null — and finding that out exposed the real noise floor

| `DSV41_IO_THREADS` | TTFT | decode | accept_len | hit | NVMe |
|---|---|---|---|---|---|
| 4 | 7.44 s | **6.92 tok/s** | 3.79 | 0.8984 | 196.1 GB |
| 12 (default) | 8.07 | 6.34 | 3.71 | 0.8916 | 212.2 |
| 24 | 8.22 | 6.36 | 3.39 | 0.8997 | 203.3 |

Read naively that is **+9 % from cutting the default by three**, and it would have been a nice
result. It is not real.

**Acceptance cannot depend on how many I/O threads the expert loader runs** — it is a property of
the drafter and the model. Yet it varies **3.39 to 3.79, 12 %**, across these three arms, and

| arm | tok/s | accept | **steps/s** |
|---|---|---|---|
| 4 threads | 6.92 | 3.79 | 1.826 |
| 12 threads | 6.34 | 3.71 | 1.709 |
| 24 threads | 6.36 | 3.39 | **1.876** |

The ordering **inverts** — 24 threads becomes the fastest per step — and the spread collapses to
noise. The honest conclusion is **no measurable effect**, which *confirms* the offline finding
(saturates by 4, default 12 is already past it) rather than overturning it.

**The general lesson is worth more than the null.** `accept_len` is an uncontrolled variable with a
~12 % spread that multiplies throughput one-for-one, so **any A/B on this bench smaller than ~12 % is
unreliable unless acceptance is matched or divided out**. Re-checking tonight's other results on

| result | tok/s claim | survives normalisation? |
|---|---|---|

So three of tonight's four positive results hold up and the small one does not. `steps/s` should be

### 15b. The CB3 trace was collapsing, and the cause was a dtype *reinterpretation*, not CB3

The retry ran and `== VOID ==` fired correctly this time (pipefail works). But the trace it produced
before dying was already wrong, and the shape of the wrongness is the useful part:

| layer | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| experts touched (CB3, broken) | 383 | 379 | **217** | **54** | **29** |
| experts touched (FP4 reference) | 383 | 378 | 377 | — | — |

A clean progressive collapse — exactly what a small numerical error compounding through the residual
stream looks like, and exactly what one would wrongly conclude "3-bit experts destroy the model" from.

**The cause.** `CodebookSim.requant_packed` wants **raw bytes**: uint8 nibble pairs, and uint8 UE8M0
*exponent codes* which it turns into `2^(s − 127)`. The checkpoint stores the scale as `F8_E8M0`, and
`.float()` on that dtype **decodes** it to the value it represents. So passing it straight in computed
`2^(value − 127)` instead of `2^(exponent − 127)` — scales wrong by an exponential. The arena path
never hits this because `CB3ArenaV2.load_slot` views both tensors as uint8 first
(`cb3_moe.py:424-425`); my `DSV41_REF_CB` patch did not.

Fixed with an explicit `.view(torch.uint8)` on both, and verified: **383 / 378 / 376** against the
reference's **383 / 378 / 377**.

**The OOM was separate and mundane**: the tracer needs the GPU and the server holds 82 GB of arena.
The job's own script stops the server, but my first smoke test did not — 97 GB used before, 3 GB
after stopping. `AHEAD` lowered from 2 to 1 as well, since two concurrent 7.4 GB shard fetches add
page-cache pressure across a 40-layer run.

Worth noting what nearly happened: this would have produced a plausible-looking quality catastrophe
for CB3, in a job whose entire purpose is to judge CB3's quality. The only thing that flagged it was
the expert-touched count in the tracer's own progress line — a number printed for a different reason
entirely.

### 16. CB3 quality: **it costs 0.88 pp of coding top-1**, and its lower NLL is a calibration artifact

The CB3 arm finished at 05:49 on 2026-09-14: all 40 layers re-traced through `tools/v41_ref.py`
with `DSV41_REF_CB=3`, same corpus (`trace_corpus_v3.jsonl`, 95 sequences, 17,704 tokens), same
head, same fp8 activation fake-quant as the FP4 arm in `results/trace-unmasked-20260913`. Same
`n` in both categories, so it is a properly paired comparison and not two different corpora.

The stored means looked, at first read, like CB3 *wins*:

| | FP4 (A) | CB3 (B) |
| --- | --- | --- |
| coding NLL | 0.9965 | **0.9642** |
| coding top-1 | **81.55 %** | 80.67 % |
| general NLL | 3.3500 | **3.2231** |
| general top-1 | 46.88 % | 46.82 % |

Lower NLL *and* lower top-1 on the same tokens is the signature of a softened distribution, not of
a better model, so I did not take the NLL column at face value. `teacher_forced_check.json` only
stores means, so I wrote `tools/paired_nll.py`: both arms keep `state/after_layer39.pt` for the
same sequences in the same order, so the final norm + head can be re-run over each and the two NLL
vectors paired token by token. Three things came out of it (`results/cb3_vs_fp4_paired_nll.json`):

1. **The NLL gap is real and significant.** Paired Δ = −0.0323 ± 0.0066 on coding (t = −4.9),
   −0.1269 ± 0.0172 on general (t = −7.4). Pairing matters: the between-sequence variance is what
   would otherwise have swamped it.
2. **The top-1 loss is real and significant too, on coding.** McNemar over the discordant pairs:
   coding 239 tokens FP4-right/CB3-wrong vs 138 the other way, z = 5.20, p = 2e-7. General is a
   null: 238 vs 234, z = 0.18. Top-1 agreement is 96.7 % (coding) / 92.4 % (general), i.e. CB3
   changes the argmax on 3.3 % / 7.6 % of positions.
3. **The NLL win is softening, not information.** CB3's mean predictive entropy is higher in both
   categories (coding 0.578 vs 0.505 nats; general 1.712 vs 1.576). And the control settles it:
   sweeping a single temperature over the *FP4* arm's own logits (T = 0.60…2.50) reaches pooled NLL
   **1.6559 at T = 1.40**, against CB3's 1.7588 at T = 1. Temperature alone on FP4 beats CB3 by
   more than CB3 beat FP4. The checkpoint is overconfident on this corpus; 3-bit requantization
   noise happens to soften it, and NLL pays for calibration.

**Verdict.** For our serving path the operative metric is the argmax — decode is greedy and the
DSpark verify step compares argmaxes — so CB3 costs **0.88 pp of coding top-1** and buys nothing on
quality. What it buys is on the other axis: 211.6 GB instead of 296 GB on disk, and a miss that is
6–12× cheaper than the FP4-plus-repack path (§6, §6c). That is the trade to state when the cache is
offered: *3-bit experts are a capacity and I/O decision, and they are not free — budget roughly one
point of coding top-1 for them.*

Caveats, stated because they bound the number: this is teacher-forced next-token agreement on 17.7 k
tokens of one corpus, not a task benchmark; it measures the *reference* implementation, not the
engine (the engine additionally has fp8 head and `DSV41_DENSE_FP4=attn,wo_a` on); and a 0.88 pp
top-1 delta does not translate linearly into any downstream score. The right follow-up, if 3-bit
ever becomes the default rather than an option, is a real task eval, not more NLL.

### 17. With the arena pinned, `MAX_SEQ` is **null** — §7's 7 % was coverage, not the indexer

`sweep-max-seq-pinned`, 2026-09-14, `ARENA_GB=79` in `.env` so the swept variable cannot move
coverage. Both arms confirmed at **79.0 GB = 5465 slots (36 %, pinned)** in their captured arena
lines, which is the check §7 did not have. Same 62-token prompt, 512 output tokens, 3 runs per arm,
each arm a fresh server.

| `MAX_SEQ` | indexer columns | TPOT | decode | expert hit | NVMe/run |
|---|---|---|---|---|---|
| 4096 | 2,049 | 164.6 ms | 6.074 tok/s | 0.8878 | 224.8 GB |
| 32768 | 16,385 | 164.5 ms | 6.080 tok/s | 0.8885 | 219.1 GB |

**0.1 % apart on decode, 0.1 ms apart on TPOT, and the hit rate does not move.** An 8× range of
indexer columns costs nothing measurable.

**So §7 was wrong about the cause and I am withdrawing that half of it.** The unpinned sweep's
7.0 % was real, but it was the arena: `max_seq` sizes the `ckv`/`ik`/window caches, the arena is
auto-sized from what is left, and the hit rate fell 0.9014 → 0.8943 across those arms. Pin the
arena and both the hit-rate movement and the decode movement disappear together. §7's own table
already contained the evidence — the cost was not linear in columns (+2,048 columns cost +5.7 ms,
+12,288 cost +6.1 ms) — and I read that as "not *cleanly* the indexer" when it should have been
read as "not the indexer at all".

**What this retracts.** §7 said this "is the same defect class vLLM fixed in #56686 for +5.0 %, and
confirms the shape is live here". It does not. At this context there is no `max_seq`-proportional
decode cost to win back.

**What it does not retract.** The benchmark prompt is 62 tokens, so ~31 live positions. This says
the indexer's *allocated* width is free; it says nothing about the indexer's cost at 20k real
positions, which is a prefill question and still open (TODO prefill item 4). Do not generalise this
cell past short context.

**Secondary reading, for the arena curve.** Both pinned arms sit at 6.07–6.08 against the auto
default's 6.24 (§14) at 82–83 GB. Pinning down to 79 GB costs ~2.5 % of decode for ~1 pp of
coverage, which is consistent with §12's curve and is a third independent point on it.

### 18. Cross-layer expert prediction, on the metric that matters: **~32 %**, not 70–80 % and not 2 %

Third-party proposal (2026-09-14): a transition-table predictor, no neural net —
`M[i,j][a,b] ≈ P(b active at layer j | a active at layer i)`, scored as
`score_j(b) = bias_j(b) + Σ_{a∈top6_i} g_a · M[i,j][a,b]` — evaluated **not** on exact token→expert
accuracy but on the *set* a decode step needs, and scored by **the fraction of real cache misses
converted into prefetched hits at a bounded overfetch budget**. Their stop-line was 70–80 % at 1.5×.

§5 already killed a co-occurrence predictor, so the first move was to check whether that applies.
It partly does not: §5 measured recall of a *token's* top-6 and then costed it inside a timing
model. The set framing deserved its own number. `tools/xlayer_predict.py`, on the 17,704-position
unmasked trace, split **by sequence** (a table trained on the sequence it scores reads its own
answer back), resident set = hottest 5,465 of 15,360 pairs = the engine's real arena:

| d | true/step | miss/step | ×1.00 | ×1.25 | ×1.50 | ×2.00 | popularity |
|---|---|---|---|---|---|---|---|
| 1 | 22.5 | 8.6 | 26.7 % | 30.4 % | **33.7 %** | 39.4 % | 4.5 % |
| 2 | 22.4 | 8.6 | 26.4 | 30.1 | 33.4 | 39.0 | 4.4 |
| 4 | 22.3 | 8.6 | 25.5 | 29.2 | **32.4** | 38.0 | 4.3 |
| 8 | 22.5 | 8.7 | 24.1 | 27.7 | 30.9 | 36.3 | 4.4 |
| 12 | 22.7 | 8.7 | 23.8 | 27.4 | 30.5 | 35.9 | 4.6 |
| 16 | 22.6 | 8.6 | 23.5 | 27.0 | **30.1** | 35.5 | 4.7 |

**Three readings, in order of how much they change the plan.**

1. **Distance barely costs anything.** 26.7 % at d=1 falls only to 23.5 % at d=16. This contradicts
   the proposal's own design assumption that a rolling 4-layer horizon is needed to keep accuracy —
   here you can take the *full* 16-layer lookahead, buy 4× the time budget, and pay 3 pp. If this
   avenue is built, build it with a long horizon.
2. **The signal is real and it is not popularity.** 32.4 % against a 4.3 % static-frequency
   baseline at the same budget: **7×**. §5's popularity baseline was 14.4 % and this reproduces it
   exactly (14.3–14.8 %) when the residency filter is removed, which is the control that says the
   two measurements are on the same footing.
3. **It is still below the stop-line, and the cost is the reason.** At ×1.50 you issue 13 reads to
   convert 2.8 of 8.6 blocking misses: **+118 % of read bytes to remove ~32 % of blocking misses.**

**Why my first attempt said 4.3 % and was wrong.** One transition table pooled over all `(i, i+d)`
pairs instead of one per source layer. Pooling halves the recall (16.8 % vs 45.1 % at ×1.5, no
residency filter) — the transitions are layer-specific, which is the whole reason the signal exists.
Recorded because the broken version sat *at* the popularity baseline and looked like a clean kill.

**Two caveats that bound the 32 %, both pushing the same way.**
* The resident set here is a static top-5,465 covering 77.4 % of decisions, while the live engine
  measures an 88–89 % hit rate. So this miss set is roughly twice too large and skewed toward more
  popular — hence easier — experts. **32 % is an optimistic ceiling, not a forecast.**
* This is the reference trace (teacher-forced, ≤512-token sequences), not a live decode stream, and
  it ignores timing and eviction entirely. §5's 2.3–4 % came from costing the same signal *inside* a
  timing model. The truth is between the two, and the gap between 32 % and 4 % is exactly "does the
  prefetch land before the layer runs, and survive to be used".

**Verdict: not dead, not ready.** The deciding question is not accuracy, it is whether the +118 %
of reads is free. §13 measured NVMe at 2.3–3.0 GB/s of an available 5.0–6.8, so there *is* spare
bandwidth — which is the proposal's strongest argument and our own data supports it. But the same
§13 also says the engine is schedule-bound, and an unblocked loader (TODO decode item 6, 1.25–1.35×,
bit-exact) captures the idle bandwidth **without** a predictor, without overfetch, and without a
training set. That ordering stands: pipeline the loader first, then re-ask this question against the
pipelined baseline, where the answer may well be different.

### 19. The decode breakdown, on a correct instrument: **resolve is 95 % of decode wall**

Replaces the withdrawn §10c. Three **separate processes**, 700-token request on a B-tree prompt the
model does not finish early, fresh server on the fixed snapshot (`605f09d`), `prefill_misses 0` in
every run — which is the assertion that the boundary is where it claims to be.

| start | decode wall | misses/step | resolve share | of resolve: load-wait | route bookkeeping |
|---|---|---|---|---|---|
| 1 | 118.2 s | 448 | 95 % | 79 % | 21 % |
| 2 | 113.0 s | 475 | 95 % | 79 % | 21 % |
| 3 | 111.6 s | 464 | 95 % | 79 % | 21 % |

**Identical to the digit across three processes.** §10c's *conclusion* — that `resolve()` is
essentially the whole decode step — was right; its evidence was not. That is worth stating plainly
rather than quietly: the withdrawal was correct and so was the claim.

**The new part is the split inside `resolve()`.** Waiting on NVMe is 79 %; the other **21 %** —
about 20 % of decode wall — is inside `route_s`, at **12.7 ms per layer**.

> **I first wrote that 21 % up as "pure host Python" and that is wrong — measured, same day.**
> `tools/route_host_micro.py` replays `resolve()`'s entire host path on the **real recorded routes**
> (`route-11k.jsonl`, 247 decode calls, 22.8 unique experts each) with no GPU and no copy:
> `np.unique`, both resident/miss passes, the LRU `move_to_end`, the transient ring, the LUT build
> and the gather. It costs **0.010 ms per call — 0.1 % of `route_s`.** Optimising that Python would
> buy 0.02 % of decode wall.
>
> **What `route_s` actually is:** the first statement of `resolve()` is
> `experts.to("cpu", dtype=torch.int32, non_blocking=False)` — a **blocking device→host copy**, and
> the timer starts before it. So `route_s` is overwhelmingly *the host waiting for the GPU to tell it
> which experts this layer needs*. `[derived from the code, not yet isolated — queued as
> `route-sync-probe`: put a `torch.cuda.synchronize()` before the timer and see whether `route_s`
> collapses.]`
>
> That is a better finding than the one it replaces, because it names the actual shape of the
> schedule problem: **the host cannot issue a read until the GPU says what to read, and the GPU
> cannot continue until the read lands.** The 79 % and the 21 % are two halves of one serialization,
> not two independent targets.

**Two things the table is not.**

* **The levels are not the serving levels.** 448–475 misses/step against the benchmark's ~133. A
  700-token generation on a fresh server never reaches the steady state the 512-token headline arms
  do. The *shares* reproduce exactly across three starts; the per-step costs do not transfer.
* **`attn_s` and `moe_s` read 0.00, and that is not evidence that compute is free.** The CUDA-graph
  decode path never updates `m.stats` — those counters are written by the eager `Model.block` path,
  which decode does not take. We still have no GPU-side decode breakdown; §6 of the field survey's
  "~1,600 dependent launches, no kernel above 3 %" remains the only estimate of one.

**Why `step-breakdown-2` reported the old contaminated numbers anyway**, and the harness lesson in
it: the fix was in the file, but the **server was still running pre-fix code**. A qnext job's
`recover` only runs when the **guard fails** — and the guard is a health check, which passed. So a
code fix never reaches a healthy server, and the job's own note ("the recover line does that") was
wrong about its own harness. Proof was direct and took one probe: `decode_only` equalled the whole
request *exactly* (689/689 misses, 17.44/17.44 GB), which is a snapshot of zeros. `__pycache__`
cleared and server restarted, `prefill_misses` in decode went to 0.

### 20. CB2 costs **2.16 pp of coding top-1** — 2.5× CB3's, and it breaks CB3's general-category null

`cb2-nll`, 40 layers re-traced at `DSV41_REF_CB=2`, same corpus and head, paired token by token
against **both** prior arms (`tools/paired_nll.py`). The ladder:

| | coding top-1 | vs FP4 | general top-1 | vs FP4 | entropy (coding) |
|---|---|---|---|---|---|
| FP4 | **81.55 %** | — | **46.88 %** | — | 0.505 |
| CB3 | 80.67 % | −0.88 pp | 46.82 % | null | 0.578 |
| **CB2** | **79.40 %** | **−2.16 pp** | **45.71 %** | **−1.18 pp** | 0.683 |

Both losses are significant and neither is marginal: coding McNemar 446/200, **z = 9.68**; general
372/299, **z = 2.82**. Against CB3 directly, CB2 loses a further 1.27 pp coding (357/212, z = 6.1)
and 1.11 pp general (320/251, z = 2.9).

**Three readings.**

1. **CB2 is 2.5× CB3's cost on coding, and it is worse than linear in the bit.** 4→3 bits costs
   0.88 pp; 3→2 bits costs another 1.27. The checkpoint is FP4-native at ~2.6 effective bits, so
   CB2 is the first format below what is actually stored, and it shows.
2. **It breaks the one thing CB3 preserved.** CB3's general-category top-1 was a clean null
   (−0.06 pp, z = 0.18). CB2's is a real −1.18 pp. The damage is no longer confined to code.
3. **The NLL/softening story repeats and is worse.** CB2's entropy is 0.683 against FP4's 0.505 —
   softer than CB3's 0.578 — and on coding its NLL is now *worse* than FP4 (+0.012 ± 0.010) while
   general is still "better" (−0.19). Temperature alone on FP4 reaches pooled NLL **1.656 at T = 1.40**
   against CB2's 1.765. Same artifact, same control, same verdict.

### What this closes

The CB2 all-resident design was the last arithmetically possible profile-free one on this box:
220 experts/layer at 9.99 MB = **87.9 GB**, against ~88 GB reachable with the dense/head savings, at
a 57.3 % keep that sits above the 0.44 which degenerates and just under the 0.60 which passes
(§ cliff). It is now priced, and the price compounds:

* **≥ 2.16 pp of coding top-1 from the format alone**, before any pruning;
* **plus an unmeasured pruning cost** — 220/384 keeps ~94 % of coding and ~90 % of general
  gate-weight mass (`universal_keepset.py`), and keep-0.60 passed only the *degeneration* gate. Its
  top-1 cost has never been measured, and after §16 we know a gate that detects degeneration can
  miss a point of top-1 entirely.

For scale: on the Qwen side a **0.42 pp** fidelity difference was treated as decision-relevant. This
is five times that from the quantizer alone.

**So: all-resident is closed on this box.** Not because it does not fit — it does, at 87.9 GB — but
because it costs more quality than the two levers that cost none. The prompt cache already puts turn
2 at **~21 s at any context** (2.85× / 5.83× / 9.12× measured), and the layer-major transpose is a
measured **3.88×** on prefill I/O. Both are bit-faithful to the full 384-expert router. Spending
2–3 pp of coding accuracy to buy speed we can get for free is the wrong trade, and this is the
measurement that says so rather than an argument that guesses it.

**CB3 stays the serving format** at its measured 0.88 pp, for 211.6 GB instead of 296 GB on disk and
a 6–12× cheaper miss. **CB2 is not a serving candidate.**

### 21. `route_s` **was** the device wait — confirmed, 14.4× collapse, and the decode step finally decomposes

`route-sync-probe`, A/B on `DSV41_ROUTE_SYNC`, three **separate processes** per arm. The ON arm
synchronizes before the `resolve()` timer starts, so the device wait lands in `sync_s` instead of
inside `route_s`.

| | `sync_s` ms/step | `route_s` ms/step | route share of `resolve()` |
|---|---|---|---|
| OFF ×3 | 0 / 0 / 0 | 506.8 / 515.4 / 551.8 | 21 / 21 / 20 % |
| ON ×3 | 494.1 / 515.4 / 537.5 | **34.5 / 37.7 / 37.0** | **2 / 2 / 2 %** |

**`route_s` falls 525 → 36 ms/step, a 14.4× collapse, and `sync_s` picks up 516 ms/step — the same
time, renamed.** The hypothesis is confirmed: the first statement of `resolve()` is a blocking
`experts.to("cpu", non_blocking=False)`, the timer opened before it, and 99 % of what looked like
routing was the host waiting for the GPU to say which experts this layer needs.

**So the decode step decomposes, for the first time, into three things that are actually different:**

| | share of decode wall |
|---|---|
| waiting for NVMe reads | **75–76 %** |
| waiting for the GPU to produce the routing | **18 %** |
| host bookkeeping (`np.unique`, LRU, ring, LUT) | **1.5 %** |

Reproduced to within a point across three processes per arm.

**What this settles, and what it moves.**

* **§19's "79 % / 21 % inside `resolve()`" was two halves of one serialization**, exactly as
  suspected — not two independent targets. With the wait named, `resolve()` is 98 % load-wait.
* **The bookkeeping is 1.5 % of decode wall.** My §19 draft called it "~20 % of decode wall in pure
  host Python" and named `np.unique` and the LRU as the target. That was wrong by more than an order
  of magnitude and is now wrong on the engine as well as in the offline microbenchmark. Optimising
  that code is worth nothing.
* **The 18 % is the real second lever, and it is not removable by making anything faster** — it is a
  data dependency. The host cannot issue a read until the GPU names the expert. The only ways at it
  are to issue reads *before* the routing exists (§18's transition predictor, 32 % of misses at 1.5×
  overfetch; and the shared/dense weights of layer L+1, which need no prediction at all), or to stop
  blocking the host thread on the copy so layer L+1's dense work can start.
* **The 75 % is the loader pipeline's target** and it is now sized properly. At the benchmark's
  steady state we move 3.2 GB/s of an available 5.0–6.8, so the headroom there is ~2.2×.

**Caveat on the ON arm, stated because it is easy to misread:** the sync costs a full device
synchronize per layer, 40 per step, and the ON arm's totals are *not* a faster configuration — decode
wall is 108.9–118.0 s against OFF's 111.4–119.5 s, i.e. the same within noise. The gate exists to
*attribute* time, never to save it, and the code says so.
