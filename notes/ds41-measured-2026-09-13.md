# DeepSeek-V4.1-Flash, measured on the box — routing, residency, read path

2026-09-13. Everything below is DS4.1's own routing, not Qwen's. Until today every residency number
we had was measured on Qwen3.8-Flash-Next and carried the caveat "the directions transfer, the levels
do not". Several of the levels turned out not to transfer, and one direction reverses.

## How the trace was taken

`tools/expert_trace.py` in the fork streams the model **one layer shard at a time**: every sequence
is pushed through layer L (one 7.4 GB shard) before layer L+1 is touched, so at most one layer's
weights are live and the 510 GB checkpoint never has to be resident. The 40 layer shards came off the
backup server over LAN at 103 MB/s, two ahead of the tracer, deleted behind it; peak local footprint
was three shards. Engram rows for layers 1 and 14 were pulled by HTTP range request — 5,034 requests,
66 MB, 61 s — instead of the two 101 GB tables. Corpus: `trace_corpus_v3.jsonl`, 95 sequences,
17,704 tokens, coding + general. Wall time 51 minutes for 40 layers.

The router is **unmasked** — this is what the model actually wants to route to, not what
`PRUNE_KEEP` leaves routable. The port validated end to end on the same pass: teacher-forced top-1
accuracy **81.6 % on coding (NLL 0.996)** and 46.9 % on general (NLL 3.350).

Trace: `notes/data/ds41-routing-unmasked.npz` (57 requests after dropping sequences under 64 tokens,
40 layers, top-6, 384 experts). Run log and full output in `notes/data/ds41-*-20260913.txt`.

## 1. The arena is 34 %, not 44 %, and the traffic is 0.58 GB/token

`EXPERT_BYTES = 3 × (2304×2560 + 2304×160) = 18,800,640` (`engine/experts.py:46`), which the shard
headers confirm: six tensors per expert, 17.93 MiB, laid out as **two runs** — a 1.05 MiB scale run
and a 16.88 MiB weight run about 585 MB apart, each starting unaligned (offset mod 4096 = 3896 and
1592), so O_DIRECT overreads exactly one page per run: **8 KiB on 18.8 MB, 0.04 %**. That is
negligible, as ds-08 said.

So a 98 GB arena is **5,212 slots = 33.9 %** of the 15,360 (layer, expert) pairs, and 90.5 GB is
4,813 = 31.3 %. The 44 % we have been quoting is a CB3 3-bit number, from the packing the
`<!DOCTYPE>` degeneration pulled back from.

Simulating `ExpertStore` faithfully — one global LRU keyed `(layer, expert)` across all 40 layers,
plus the FIFO ring that absorbs prefill misses — over a held-out stream of 12 requests:

| arena | slots | best coverage | misses/token | **GB/token** |
|---|---|---|---|---|
| 98 GB | 5,212 (33.9 %) | 83.9 % | 31.0 | **0.582** |
| 90.5 GB | 4,813 (31.3 %) | 81.9 % | 34.0 | 0.639 |
| 60 GB | 3,191 (20.8 %) | 73.5 % | 50.6 | 0.951 |

**This is the number that reframes the project.** The survey assumed 271 MB/token at ~93 % coverage.
The real figure at the shipped arena is **0.582 GB/token at 83.9 % coverage** — more than twice the
traffic, because both inputs were wrong: the arena is 34 % not 44 %, and coverage is 84 % not 93 %.

At the read rate the engine's own reader actually achieves (section 3, 5.2 GB/s at one expert in
flight) that is **112 ms/token of NVMe alone, an 8.9 tok/s ceiling** for the full-quality unpruned
path even with a perfect schedule. At the 2.68 GB/s it measures today it is 217 ms/token → 4.6 tok/s,
which is where the observed 2.68 tok/s comes from once compute is added.

The consequence for the roadmap: fixing the schedule is worth about 2×, and then the path is **still
bandwidth-bound**. Everything beyond that has to remove bytes, not reorder them.

## 2. Their residency design is right, and their code default is not

Coverage at the 98 GB arena, varying only `transient_slots` (the FIFO ring that keeps a long prompt
from evicting the decode working set):

| transient | cold start | with the global warm start |
|---|---|---|
| 0 (prefill into the LRU) | 82.04 % | 82.51 % |
| **8** (`env.example`) | 82.80 % | **83.88 %** |
| 100 | 82.66 % | 83.69 % |
| 400 (the code default) | 81.90 % | 82.71 % |
| 1000 | 80.46 % | 81.09 % |

* The ring earns its slots: 8 beats 0 by **+1.4 pp**. Their reasoning holds on their own model.
* But `ExpertStore.__init__` defaults `transient_slots=400`, which is **−1.2 pp** against the 8 that
  `env.example` sets. Anyone constructing the store in Python without the env file gets the worse
  number. Change the default to 8.
* The global warm start is worth **+1.0…+1.1 pp** at every ring size — small, free, keep it.
* **One global pool beats per-layer budgets** (82.71 % vs 82.22 %), confirming ds-05 on DS4.1.

Prefill-warming — seeding the arena from the request's own prompt — is **negative here**: −5.1 pp at
34 %/10 % dynamic, −3.1 at 20 %/10 %, +1.2 at best. The prompts in this corpus are 17–31 tokens, well
under the 256–1,024 that ds-10 found necessary, so this is consistent with Qwen rather than new
evidence. Closed on both models.

## 3. The read path is not the problem — and neither of the two config levers is real

`tools/expert_read_bench.py` imports the engine's own `ExpertStore` and times `_read_leased`, so this
is the shipped code, not a re-implementation. Median of 3, 48 expert reads per cell, on real shards:

| `DSV41_IO_THREADS` | conc 1 | conc 2 | conc 4 | conc 8 |
|---|---|---|---|---|
| 1 | 4.94 | 5.23 | 5.29 | 5.21 GB/s |
| 2 | 5.04 | 5.60 | 5.89 | 5.77 |
| 4 | 5.08 | 5.67 | 5.87 | 6.21 |
| 12 (default) | 5.04 | 5.67 | 6.11 | 6.14 |

and varying `DSV41_READ_CHUNK_MB` at 12 io-threads: 2 MB → 4.68/5.82/6.13, 4 MB (default) →
5.18/5.49/6.18, 8 MB → 5.05/5.93/6.26, unsplit → 5.20/5.96/6.42 at conc 1/2/4.

* **`DSV41_IO_THREADS` is not a lever.** It saturates by 4 and the default is 12; a decode layer
  misses 0.5–1.6 experts, so the staging semaphore never binds. Survey idea 2a is dead.
* **`DSV41_READ_CHUNK_MB` is not a lever either.** Reading the expert unsplit is worth perhaps 3–8 %
  at one expert in flight and nothing beyond that. My earlier +41 % was a serial-chunking harness,
  not this engine — withdrawn this morning, and this is the measurement that settles it.
* **The read path gives 5.0–6.4 GB/s. Decode measures 2.68.** So roughly half the load phase is
  spent *outside* `_read_leased` — in the staging lease, the H2D and its `stream.synchronize()`, and
  above all in `resolve()`, which does `list(self.pool.map(...))` and therefore **blocks the whole
  layer on its misses before the MoE runs**, 40 times per token, with nothing overlapping across
  layers. That is where the missing 2× is, and it is a structural fix, not a constant.

## 4. Widening the verify block is sublinear in bytes

Distinct experts a layer touches over k consecutive decode tokens, measured:

| block k | distinct/layer | per step (40 layers) | marginal | per verified token |
|---|---|---|---|---|
| 1 | 6.00 | 240.0 | | 240.0 |
| 2 | 10.13 | 405.3 | +4.13 | 202.6 |
| 4 | 16.87 | 674.9 | +3.17 | 168.7 |
| **6** | **22.56** | **902.5** | +2.74 | **150.4** |
| 8 | 27.53 | 1101.1 | +2.39 | 137.6 |

The stored 20.96 experts/layer at block 6 was 7 % low; the real figure is 22.56. More usefully, the
marginal cost of a position **falls** from +4.13 to +2.39 experts per layer, so per *verified* token
the arena traffic drops 240 → 137.6 from k=1 to k=8 — widening is sublinear and, in bytes, free.

This does not by itself resolve the verify-width conflict, and it is worth being precise about why.
Per *accepted* token the sign can flip: at ~3.1 accepted of 6, block 6 costs 902.5/3.1 ≈ 291 expert
reads per accepted token and block 8 at ~3.4 accepted costs 1101/3.4 ≈ 324 — rising. So the stored
"+13.1 ms per +2 positions" is compatible with everything here, and the quantity that decides it is
**acceptance as a function of k**, which this trace cannot give (there is no drafter in it). That is
the measurement to take next, and it is small.

## 5. Prediction is worth far more on DS4.1 than on Qwen

The oracle arm — a static core ranked on the held-out request's own decode histogram, which no
serving system can have — brackets what any smarter *choice of contents* could win:

| model | arena | best real arm | oracle | headroom |
|---|---|---|---|---|
| Qwen Flash-Next | 44 % | 92.4 % | 97.1 % | ~5 pp |
| **DS4.1** | **34 %** | **83.4 %** | **96.9 %** | **~13 pp** |
| DS4.1 | 20 % | 77.8 % | 88.7 % | ~11 pp |

At 34 % the oracle needs **7.5 loads/token against the best real arm's 39.8** — a **5–6× reduction in
NVMe bytes**, on the term that section 1 shows is the binding constraint. On Qwen the same experiment
said prediction was worth about five points and not worth building. On DS4.1 it is the largest single
number in this document.

That reverses the survey's ranking. Drafter-driven expert prefetch was ranked last there, on Qwen-era
reasoning that lookahead is expensive and the union inflates. Here the prize is not latency hiding,
it is **bytes**: any mechanism that identifies the ~34 % of experts this request will actually use,
before it uses them, is worth up to 5× on the bottleneck. DSpark is the checkpoint's own drafter and
shares its router. That experiment should be near the top of the list, not the bottom.

## What to do next, in order

1. **Unblock the layer serialisation in `resolve()`** — the missing 2×, and bit-exact. The read path
   is already fast; nothing overlaps it.
2. **Measure acceptance as a function of block size**, which settles the verify-width conflict and
   costs a short run.
3. **Test drafter-derived expert prediction offline** against this trace: replay it, count how many
   of the target's layer-L experts the drafter's routing already names. Section 5 says the ceiling is
   5×; this says how much of it is reachable.
4. Change `transient_slots`'s code default from 400 to 8 (−1.2 pp today for anyone not using
   `env.example`).
5. Do **not** spend time on `DSV41_IO_THREADS`, `DSV41_READ_CHUNK_MB`, per-layer arena budgets, or
   prefill-warming. All four are measured dead.
