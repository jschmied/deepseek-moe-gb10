**Why it matters more than it looks.** There is currently **no way to measure memory-system
utilisation on this box.** Measured today, not assumed:

* `tegrastats` is **not installed** — no EMC counter;
* `ncu` is **not installed**;
* `nsys` 2025.3.2 *has* the right metric set (`gb10b`, this exact chip) but refuses with
  `ERR_NVGPUCTRPERM`;
* **`nvidia-smi dmon`'s `mem %` is stubbed on this iGPU** — under a saturating 8192³ matmul `sm %`
  goes to 96 while `mem %` stays **0**, and `fb`/`bar1` report `-`.

So the profiling permission is the only route, and the open question below cannot be answered
without it.

## 3. The open question

**Overlapping expert copies with MoE kernels slows the FFN by 32 %** — at about **6 % of this box's
measured 240 GB/s stream rate**. Nothing is bandwidth-saturated, so the mechanism is *not* known.
Live candidates, which have different implications:

* **L2 pollution** — 13.77 MB streamed per copy against the kernel's working set;
* **memory-controller latency interference** well below saturation;
* **driver/launch contention** from twelve worker threads each doing stream ops plus a synchronize —
  weakly supported by `io_threads=4` being the marginally *best* arm.

If it is bandwidth, the loader-pipeline family is capped by hardware. If it is L2 or launch
contention, those have implementation answers (non-temporal or chunked copies, fewer workers, a
different staging route) and the family is alive. **That is what the profile decides.**

A third party proposed a clean discriminator that needs no profiler —
**read-early / install-late**: do the NVMe read during attention but defer the arena H2D to the layer
boundary, so no arena write overlaps a kernel. It needs one change first: the pinned staging pool is
`io_threads` buffers (12), and holding a layer's ~153 reads needs **153 buffers ≈ 2.1 GB pinned**, so
`DSV41_STAGE_BUFS` must be decoupled from `io_threads`. That 2.1 GB costs ~145 arena slots ≈ 0.9 pp
of coverage, which the result has to beat.

## 4. What is closed, so nobody reopens it

Most of today's value is here.

| | |
|---|---|
| **CB2 (2-bit experts)** | costs **2.16 pp** of coding top-1 (paired, McNemar z = 9.68); breaks the general-category null CB3 preserved. Not a serving candidate |
| **Pruned all-resident** | degenerates between keep **0.44 and 0.60** (html distinct-ratio 0.056 / 0.095 at 2000 tokens); the band that passes needs 133 GB against ~83 available |
| **Per-layer bit allocation** | **flat** — the marginal cost of the third bit spans 0.0919–0.0983 across all 40 layers, a 7 % spread. Bits cannot be moved |
| **`MAX_SEQ` as a decode lever** | **null** with the arena pinned (6.074 vs 6.080 tok/s over an 8× range of indexer columns). The old 7 % was arena shrinkage |
| **Wider verify blocks** | width 8 is **20 % worse** |
| **`io_threads`, `read_chunk_mb`, prefill chunk size** | null; 2048 is already optimal |
| **Cross-layer expert prediction** | 32.4 % of misses at 1.5× overfetch, 7× the popularity baseline — below the 70–80 % bar |
| **MTP/DSpark async backlog** | costed at **1.05×** today (the whole draft path is ~5 % of decode wall), ~1.09× after a loader pipeline. Deferred, `notes/layer-scheduler.md` |
| **Early submission** (`DSV41_EARLY_SUBMIT`) | **~1.03×**. Mechanism works (resolve 15.1 → 6.7 s) but the wall barely moves. In the tree, off by default |

## 5. Where the time goes (the map to plan against)

**Decode**, three separate processes: **75–76 % waiting on NVMe, 18 % waiting for the GPU to name
the experts, 1.5 % host bookkeeping.** Everything the model computes is ~5 %.

**Prefill**, per encoder layer under layer-major: **attn+route 53 %, resolve 19 %, FFN 28 %**.

`notes/model-dependency-graph.md` has the model's dependency structure written for someone without
the project's vocabulary, including where the I/O is and where every wait is.

## 6. Method rules this session earned

* **Verify before push.** `ast.parse` is not verification; nor is testing a helper when the call site
  is what changed. Two commits today were reverted or corrected for this. `memory/verify-before-push`.
* **A prefill harness must set `DSV41_PROMPT_CACHE=0`.** Flipping the cache default silently
  invalidated three harnesses in one afternoon, each time making a result look *better*. Varying the
  prompt is not enough — `longctx_profile` builds a longer prompt as an extension of a shorter one, so
  the cache resumes it. Assert on `prompt_cache_reused`.
* **A mechanism is a hypothesis until something measures *it*, not its consequence.** Twice today I
  promoted a plausible mechanism to an explanation — `wait_stream`, refuted by its own diagnostic; then
  "bandwidth", refuted by five minutes of arithmetic. The consequences were solid both times.
* **Three starts, separate processes**, and discard start 1 — it is the cold outlier in every arm.

## 7. Suggested order on resume

1. Apply the profiling change, reboot, run `scripts/profile-early-submit.sh`. Decide the mechanism.
2. If it is not bandwidth: `DSV41_STAGE_BUFS`, then read-early/install-late, three arms.
   If it is bandwidth: close early submission, delete nothing, move on.
3. Either way the strategic read stands: **layer-major won by moving 5.43× fewer bytes, not by
   overlapping the movement.** The next real gain is likelier to come from moving less data than
   from scheduling the same movement better — and the byte-reduction routes we had (CB2, pruning,
   per-layer bits) are all measured closed, which is itself the most useful thing to know.
4. Still unpaid by anyone in this field, us included: **a real agent-turn eval.** Every quality number
   here is teacher-forced or a synthetic gate.
